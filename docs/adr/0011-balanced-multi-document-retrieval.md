# ADR 0011: 여러 문서 질문의 문서별 균형 검색

- 상태: 채택
- 날짜: 2026-11-25
- 관련: [ADR 0009](0009-prefer-consolidated-notes.md)(연결 주석 우선 재정렬), [ADR 0010](0010-local-cascade-and-number-grounding.md)(로컬 상향·숫자 검증, 같은 실측에서 나온 개정)

## 맥락

여러 회사를 비교하는 질문은 `document_ids`에 문서를 2개 이상 넣어 검색합니다. 지금까지는 이 문서들을 한 번에 벡터 검색해 유사도 상위 `TOP_K`개(기본 8)를 가져왔습니다.

2026-11-25 실제 2025 사업보고서 3건, 25문항 비교 Eval에서 `compare-04`(삼성전자·NAVER·현대차의 외부감사인)가 이 방식의 약점을 보여 줬습니다.

- 세 문서를 대상으로 상위 8개를 검색했습니다. 기대 섹션 `V. 회계감사인의 감사의견 등 > 1. 외부감사에 관한 사항`은 **한 회사 것만** 1위로 들어왔고, 나머지 자리는 다른 섹션이 차지했습니다.
- 그래서 모든 구성(`qwen3.5:9b`, `gpt-oss:20b@low`, `qwen3:14b`, `qwen3.5:9b > qwen3:14b`)이 근거 부족으로 거절했습니다. 상향 구성에서는 이 거절이 상향까지 일으켰지만, 같은 근거를 받은 큰 모델도 답하지 못했습니다.
- 그런데도 Eval의 recall@k는 "기대 섹션이 하나라도 있으면 성공"이라 이 문항을 성공으로 셌습니다. 검색 문제가 지표에 보이지 않았습니다.

같은 질문이라도 회사마다 문서 표현과 표 구성이 달라 유사도 분포가 다릅니다. 한 회사의 청크가 전반적으로 유사도가 높으면 그 회사 청크가 상위 k를 거의 다 차지합니다. 비교 질문은 회사마다 근거가 하나 이상 있어야 답할 수 있습니다.

## 결정

1. **문서별 검색**(`answering.service.retrieve_ranked`, `BALANCE_MULTI_DOCUMENT_RETRIEVAL` 기본 `true`)
   - 서로 다른 `document_ids`가 2개 이상이면 문서마다 따로 후보를 구합니다. `search_chunks`를 `document_ids=[그 문서]`로 부릅니다. 후보 수는 지금과 같습니다(`PREFER_CONSOLIDATED=true`면 `max(TOP_K, RETRIEVAL_CANDIDATES)`, 아니면 `TOP_K`).
   - `PREFER_CONSOLIDATED=true`면 연결 주석 우선 재정렬(`prefer_statement_scope`)을 문서 단위로 적용합니다. 재정렬은 원래 같은 문서 안의 연결↔별도 쌍만 보므로 문서 단위로 적용해도 규칙은 같습니다.
2. **순위별 라운드로빈**(`answering.service.interleave_by_rank`)
   - 각 문서의 1위, 그다음 각 문서의 2위, … 순서로 `TOP_K`개를 채웁니다. 문서 순서는 `document_ids` 순서입니다.
   - 예: `TOP_K=8`, 문서 3개 → 3, 3, 2개.
   - 어떤 문서의 후보가 모자라면 남은 칸은 다른 문서의 다음 순위로 채웁니다.
   - 최종 목록은 유사도 내림차순으로 정렬해서 돌려줍니다. 답변 프롬프트의 근거 번호와 `POST /search` 결과가 유사도 순서를 유지합니다.
3. **신뢰도 규칙 유지**: `low_retrieval_score` 판정의 최고 유사도는 모든 문서 후보 중 최댓값입니다. 지금까지(한 번에 검색한 후보의 최댓값)와 같은 값입니다.
4. **바꾸지 않은 것**: 문서가 1개이거나 `document_ids`가 없으면(조직 전체 검색) 지금 동작 그대로입니다. `BALANCE_MULTI_DOCUMENT_RETRIEVAL=false`면 여러 문서도 한 번에 검색합니다. `retrieval/search.py`의 SQL과 HNSW 설정(`hnsw.iterative_scan`)은 바꾸지 않았고, 문서별로 여러 번 호출만 합니다.
5. **Eval 지표**(`evals/run.py`)
   - 새 지표 **recall@k (every document)**: 답할 수 있는 문항에서 `rcept_nos`의 **모든 문서**마다 기대 섹션 청크가 top-k 안에 하나 이상 있어야 성공입니다. 문서가 하나인 문항은 기존 recall과 같습니다.
   - 구성별 리포트의 Metrics 표와 유형별 표, 비교 리포트의 Configs 표에 이 열을 넣었습니다. 기존 recall@k는 과거 리포트와 이어서 비교할 수 있게 그대로 둡니다. 두 값의 차이가 "한 회사만 검색된" 비교 문항의 크기입니다.
   - False abstention 진단과 Citation diagnostics의 검색 결과 표에 `document` 열(회사명, 없으면 rcept_no)을 추가했습니다. 어느 회사의 청크가 자리를 차지했는지 바로 보입니다.

## 대안

| 대안 | 기각 이유 |
| --- | --- |
| `TOP_K`를 문서 수에 비례해 늘림 | 한 회사 청크가 많을수록 늘린 자리도 그 회사가 차지할 수 있음. 프롬프트가 길어져 로컬 모델 지연과 `num_ctx` 부담이 커짐 |
| 문서별 고정 할당(`TOP_K // 문서 수`) | 나머지 자리가 버려지고, 후보가 모자란 문서의 자리를 다른 문서가 쓰지 못함 |
| 문서별 점수 정규화 후 한 번에 정렬 | 정규화 방식(최댓값, z-score)에 따라 결과가 흔들리고, 점수 의미(cosine)가 사라져 `MIN_RETRIEVAL_SCORE`와 비교할 수 없음 |
| SQL 한 번에 문서별 상위 n개(`ROW_NUMBER() OVER (PARTITION BY document_id)`) | 왕복은 줄지만 거리순 `LIMIT`으로 HNSW 인덱스를 쓰는 지금 쿼리 모양과 맞지 않아 대상 청크를 모두 거리 계산할 수 있음. 검색 SQL을 바꾸는 일이라 이번 범위 밖. 비교 질문의 문서 수는 2~3개라 호출을 나누는 비용이 작음 |
| 질문을 회사별 하위 질문으로 나눔(LLM 질의 분해) | LLM 호출이 늘고, 분해 자체를 검증해야 함. 이번 범위 밖 |

## 결과와 한계

- 비교 질문의 검색 쿼리가 문서 수만큼 늘어납니다(보통 2~3번). 각 쿼리는 한 문서로 좁혀진 HNSW iterative scan이라 영향은 작습니다.
- 문서마다 자리가 보장되므로, 한 회사에만 관련 내용이 있는 질문에서는 관련이 적은 다른 회사 청크도 자리를 얻습니다. 이 청크는 유사도가 낮아 정렬상 뒤에 오고, 모델이 근거로 쓰지 않으면 영향이 없습니다.
- 라운드로빈은 순위만 봅니다. 한 문서의 2위가 다른 문서의 1위보다 훨씬 관련이 높아도 1위들이 먼저 들어갑니다. 비교 질문에서는 회사마다 근거가 있어야 하므로 이 순서를 택했습니다.
- 효과는 같은 데이터셋으로 비교 Eval을 다시 돌려 recall@k (every document)와 compare 문항의 false abstention으로 확인합니다.
