# ADR 0007: 임베딩 레이트 리밋 대응(배치 단위 재시도)과 조직 간 공유 임베딩 캐시

- 상태: 채택
- 날짜: 2026-11-24
- 관련: [ADR 0001](0001-postgres-skip-locked-queue.md)(작업 큐), [ADR 0003](0003-embedding-provider-voyage.md)(Voyage), [ADR 0005](0005-org-isolation-app-layer.md)(조직 격리)

## 맥락

2026-11-24 실제 실행에서 사업보고서(A001, 약 100만 자, 수백 개 청크)를 가져오다 문제가 생겼습니다.

- Voyage 계정에 결제 수단이 없으면 한도가 **3 RPM / 10K TPM**입니다. 그런데 `VoyageEmbedder`는 배치당 최대 100,000 추정 토큰을 쉬지 않고 연속으로 보냈습니다. 그래서 거의 모든 요청이 429(`RateLimitError`)를 받았습니다.
- ADR 0003의 결정대로 429는 작업 단위 재시도로만 처리했습니다. 배치 하나가 429를 받으면 **작업 전체가 처음부터** 다시 실행되었습니다. 이미 성공한 배치는 버려졌고, 재시도나 재처리마다 같은 텍스트의 비용을 다시 냈습니다.
- 진행 상황이 보이지 않아 사용자는 작업이 멈춘 것으로 보았습니다.

## 결정

### 1. 재시도를 두 층으로 나눈다

| 층 | 대상 | 방식 | 끝나면 |
| --- | --- | --- | --- |
| 배치 단위(`VoyageEmbedder._embed_batch`) | 429, 5xx, 연결 오류, 타임아웃, `TryAgain` | **같은 배치만** `min(EMBED_RETRY_BASE_SECONDS × 2^n, EMBED_RETRY_MAX_SECONDS)` + 지터(최대 10%)만큼 기다린 뒤 다시 보낸다. 최대 `EMBED_BATCH_MAX_RETRIES`회 | `EmbeddingError(retryable=True)` → `RetryableJobError` |
| 작업 단위(`jobs.queue.mark_failed`) | 배치 재시도를 다 쓴 경우, 그 밖의 일시 오류 | 기존과 같다(`2^attempts × BASE_BACKOFF_SECONDS`, `JOB_MAX_ATTEMPTS`) | 문서 `failed`, 한국어 원인 설명 |

- 배치 재시도는 **짧은 흔들림**(분 단위 한도 초과, 일시적 서버 오류)을 작업 안에서 흡수합니다. 작업 단위 재시도는 **긴 장애**(제공자 장애가 수 분 이상 이어짐, 워커 재시작)를 맡습니다. 이렇게 나누면 성공한 배치를 버리는 일이 없습니다.
- 재시도할 수 없는 오류(인증 실패, 잘못된 요청)는 배치 재시도 없이 바로 던집니다. 다시 보내도 결과가 같고, 한도만 소모하기 때문입니다.
- 배치 재시도와 겹치지 않도록 문서용 Voyage SDK 클라이언트의 내장 재시도는 끕니다(`max_retries=0`). SDK가 몰래 재시도하면 RPM 예산을 써 버립니다. 질문 임베딩 경로는 바꾸지 않습니다.
- 배치를 보내기 전에 `RateLimiter`(60초 슬라이딩 윈도우, `EMBED_RPM_LIMIT`·`EMBED_TPM_LIMIT`)를 통과해야 합니다. 이렇게 하면 429가 나기 전에 미리 속도를 맞춥니다. `EMBED_TPM_LIMIT`가 있으면 배치 토큰 상한은 `min(EMBED_BATCH_MAX_TOKENS, EMBED_TPM_LIMIT)`입니다. 토큰은 문자 수로 추정하므로(한국어에서는 과대 추정) 실제 사용량은 한도보다 작습니다.
- 429 메시지에 "payment method"가 있으면 프로세스당 한 번 `embedding.provider_reduced_limits` 경고를 남깁니다. 경고에는 안내 문구만 넣고 키나 응답 원문은 넣지 않습니다.

### 2. 문서 임베딩 캐시를 조직 구분 없이 공유한다

- 테이블은 `embedding_cache(key PK, model, dim, embedding, created_at)`이고, `key = sha256(model | dim | input_type | text)`입니다.
- 문서(`input_type=document`)만 캐시합니다. 키를 일괄 조회해 없는 텍스트만 보내고, **배치가 성공할 때마다** 짧은 별도 트랜잭션으로 `INSERT … ON CONFLICT DO NOTHING` 후 커밋합니다. 청크 저장 트랜잭션(청크 교체·문서 ready·작업 succeeded·감사)은 지금처럼 마지막에 한 번만 실행합니다.
- 질문(`query`)은 캐시하지 않습니다. 질문은 짧고 대부분 한 번만 나오며, 사용자가 입력한 질문 텍스트의 흔적을 조직 밖 테이블에 남기지 않기 위해서입니다.
- **조직 구분을 두지 않는 이유**
  - 같은 공시 텍스트는 어느 조직이 가져오든 같은 모델·차원·입력 유형이면 같은 벡터가 나옵니다. 조직별로 따로 저장하면 같은 비용을 조직 수만큼 냅니다.
  - 캐시에는 **텍스트도 조직 ID도 저장하지 않습니다.** 키는 단방향 해시입니다. 벡터는 검색에 쓰이지 않고 같은 텍스트를 다시 임베딩할 때만 조회됩니다. 검색은 여전히 `chunks.org_id`로 격리됩니다(ADR 0005).
  - 남는 정보는 "어떤 텍스트가 누군가에 의해 임베딩된 적이 있다"는 사실뿐입니다. 이것도 그 텍스트 전체를 이미 아는 사람만 해시로 확인할 수 있습니다. 공시는 공개 자료이므로 이 정도는 허용합니다. 업로드(TXT/MD) 문서도 같은 테이블을 쓰지만 텍스트가 저장되지 않으므로 내용이 노출되지 않습니다.

### 3. 진행률을 보인다

- 워커는 `jobs.result.progress = {stage: download|parse|embed|store, done, total}`를 짧은 트랜잭션으로 기록합니다. 같은 단계 안에서는 최소 2초 간격으로 씁니다. 이 기록은 `locked_at`도 갱신하고, 임베딩 동안에는 `JOB_LOCK_TIMEOUT_SECONDS / 3`마다 하트비트를 씁니다. 그래서 한도 때문에 오래 걸리는 작업을 멈춘 작업으로 잘못 복구하지 않습니다.
- claim할 때 `result`를 비워, 재시도가 이전 시도의 진행률을 보여 주지 않게 합니다.
- `GET /documents`와 `GET /documents/{id}`에는 최신 작업의 `progress`와 `next_retry_at`(재시도 대기 중인 작업의 `run_after`)을 **추가 필드**로 붙입니다. 웹 화면은 이를 "임베딩 120/700", "재시도 대기(한도 초과) — 14:03:05"로 보여 줍니다.

## 대안

| 대안 | 장점 | 기각 이유 |
| --- | --- | --- |
| 작업 단위 재시도만 유지하고 백오프만 늘림 | 코드 변경이 가장 적음 | 성공한 배치를 계속 버림. 3 RPM에서는 수백 배치 중 하나만 실패해도 처음부터 다시 시작하므로 끝나지 않음 |
| 분산 레이트 리미터(Redis 토큰 버킷, Postgres 행 잠금) | 워커 여러 개가 한도를 정확히 나눠 씀 | 인프라(Redis)나 잠금 경합이 늘어남. 지금 배포는 워커 1개. 워커를 늘리면 한도를 워커 수로 나눠 설정하라고 문서화함 |
| Voyage Batch API(비동기 대량 처리) | 레이트 리밋과 비용 면에서 유리 | 결과가 몇 시간 뒤에 나오므로 파일 업로드·폴링·만료 관리가 필요함. 작업 흐름이 크게 바뀜. 대량 일괄 적재가 필요해지면 다시 검토 |
| 조직별 캐시(`org_id`를 키에 포함) | 격리 규칙이 단순함 | 같은 공개 공시를 조직마다 다시 임베딩함. 텍스트를 저장하지 않으므로 격리 이득이 거의 없음 |
| 캐시에 텍스트도 저장 | 디버깅이 쉬움 | 조직 간 내용 노출 위험이 생김. 키 해시로 충분함 |
| 청크 저장도 배치마다 커밋 | 부분 결과를 바로 검색할 수 있음 | 문서가 "반쯤 ready"인 상태가 생김. 원자적 교체(재처리 시 중복 없음) 보장이 깨짐 |

## 결과

- 결제 수단이 없는 계정은 `EMBED_RPM_LIMIT=3`, `EMBED_TPM_LIMIT=9000`으로 429 없이 천천히 끝까지 갑니다. 소요 시간은 대략 `총 추정 토큰(문자 수) ÷ EMBED_TPM_LIMIT` 분입니다. 100만 자 문서는 약 110분 걸립니다.
- 재시도·재처리·다른 조직의 같은 공시 가져오기는 캐시에서 벡터를 읽으므로 추가 비용이 없습니다. `jobs.result`의 `embedding_tokens`는 실제 청구 대상 토큰만 셉니다. 캐시 사용량은 `embedding_cache_hits`·`embedding_cache_misses`로 남습니다.
- 캐시는 지우지 않으면 계속 커집니다(1,024차원 벡터 1개당 약 4KB). 모델이나 차원을 바꾸면 키가 달라지므로 이전 행은 쓰이지 않습니다. 정리는 `DELETE FROM embedding_cache WHERE model <> …`로 할 수 있습니다.
- `RateLimiter`는 프로세스마다 따로 동작합니다. 워커를 늘리면 한도를 워커 수로 나눠야 합니다. API 프로세스의 질문 임베딩은 이 리미터를 거치지 않습니다.
