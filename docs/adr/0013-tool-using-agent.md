# ADR 0013: 도구를 쓰는 에이전트(모델은 도구를 고르고, 코드가 실행·제한·검증)

- 상태: 채택
- 날짜: 2026-11-26
- 관련: [ADR 0008](0008-local-llm-ollama.md)(로컬 LLM), [ADR 0010](0010-local-cascade-and-number-grounding.md)(숫자 근거 검증), [ADR 0011](0011-balanced-multi-document-retrieval.md)(여러 문서 균형 검색), [ADR 0012](0012-note-change-analysis.md)(주석 변동 분석)

## 맥락

"삼성전자 2025 연결 부채비율과 전년 대비 변화는?"이나 "현대차 우발부채 주석에서 전년 대비 새로 생긴 약정은?" 같은 질문은 검색 한 번과 답변 한 번(기존 질문 흐름)으로 풀리지 않습니다. 재무제표 금액을 찾고, 두 번 나누고, 차이를 구하거나, 두 해의 주석을 짝지어 비교해야 합니다.

로컬 모델(Ollama)에 이런 여러 단계 작업을 그대로 맡기면 위험합니다.

- 모델이 금액을 직접 나누거나 단위를 바꾸다 틀립니다. 기존 질문 흐름의 숫자 검증([ADR 0010](0010-local-cascade-and-number-grounding.md))이 이런 답을 이미 여러 번 잡았습니다.
- 있지 않은 근거를 인용하거나, 같은 일을 반복하다 끝나지 않습니다.
- 무엇을 근거로 그 숫자를 냈는지 사람이 따라갈 수 없습니다.

## 결정

### 1. 역할 분담

- **모델**: 매 단계 도구를 부르거나(Ollama tool calling, `OllamaClient.chat_tools`) 최종 답을 냅니다. 고르는 일만 합니다.
- **코드**: 도구를 실행하고(모두 읽기 전용), 단계·시간 상한을 지키고, 모든 단계를 `agent_steps`에 즉시 저장하고, 최종 답을 검증합니다(`agent/runner.py`).
- 도구 6개(`agent/tools.py`): `list_documents`, `search_filings`(기존 `retrieve`), `read_note`·`compare_notes`([ADR 0012](0012-note-change-analysis.md)의 주석 추출·비교 엔진), `get_financials`(OpenDART 재무제표), `calculate`.
- 문서는 UUID 대신 별칭(`D1`, `D2` …)으로만 보입니다. 별칭 표는 실행마다 서버가 그 조직의 ready DART 문서로 만들고, 다른 조직 문서는 별칭이 생기지 않습니다.
- 근거 번호는 실행 전체에서 유일합니다: 검색 `S#`, 주석 `N#`(줄 `L#`), 비교 `C#`(줄 `P#`/`C#`), 재무제표 `F#`, 계산 `K#`.

### 2. 계산 도구의 출처 제한

`calculate(expression, values)`는 `ast`로 파싱해 `+ - * /`, 괄호, 숫자, `values`의 이름, `round(x, n)`(반올림은 half-up)만 허용하고 `Decimal`로 계산합니다. 속성 접근, 다른 함수 호출, `**`, 문자열, 첨자는 거부합니다.

- `values`의 값은 **이번 실행의 앞선 성공한 도구 결과에 실제로 나온 숫자**여야 합니다. 없으면 "출처 없는 값: …" 오류입니다. 비교는 `number_check.contains_number`(쉼표·점 천 단위 표기 인정)입니다.
- 수식에 직접 쓰는 숫자는 한 자리 정수와 10, 100, …, 10^12(단위 환산 상수)만 됩니다. 그래서 모델이 `38765 / 60000`처럼 어림한 값을 수식에 넣어 우회할 수 없습니다.
- 결과 `K#`은 수식, 결과, 값마다 출처 근거 번호(`F1`, `K1` …)를 남깁니다. `K#` 결과도 다음 계산의 값으로 쓸 수 있습니다.

### 3. 최종 답 검증

- 답의 `[S3]`, `[N1:L12]` 같은 표시는 실제 근거 id여야 합니다(줄 번호는 그 결과에 보여 준 줄이어야 함). 없는 것은 지우고 개수를 남깁니다.
- 답의 숫자(`extract_numbers`, 질문에 있는 숫자 제외)는 모두 어떤 도구 결과(`K#` 포함)에 있어야 합니다.
- 상태: 근거 표시가 없으면 `no_citations`, 근거 없는 숫자가 있으면 `ungrounded_number`, 도구 오류가 전체의 절반을 넘으면 `tool_errors`. 이 사유나 `step_limit`/`repeated_call`이 있으면 `needs_review`("확인 필요"), 없으면 `completed`("근거 확인됨")입니다.

### 4. 단계·시간 상한

- 한 단계에 도구 호출은 `AGENT_MAX_CALLS_PER_STEP`(3)개까지 실행하고 나머지는 버립니다(개수 기록).
- 단계가 `AGENT_MAX_STEPS`(6)에 닿거나, 같은 도구를 같은 인자로 3번 연속 부르면(세 번째는 실행하지 않음) 도구 목록 없이 한 번 더 부릅니다. 지시문은 "지금까지 모은 근거로만 답하라"이고 사유 `step_limit`/`repeated_call`을 남깁니다.
- 실행 전체가 `AGENT_TIMEOUT_SECONDS`(300)를 넘으면 `failed`(`timeout`), 클라이언트가 끊기면 `failed`(`client_disconnected`)입니다.
- 도구 결과는 `AGENT_TOOL_RESULT_CHARS`(4,000자)에서 자릅니다. `read_note`는 120줄·6,000자를 넘지 않는 범위에서 이 상한 안에 들어가게 쪽을 나누고 `offset`으로 이어 읽습니다.

### 5. SSE로 진행을 흘려보냄

`POST /agent/runs`는 응답을 `text/event-stream`으로 열고 `run` → `step`… → `answer`(또는 `error`) → `done`을 보냅니다. 실행은 API 프로세스의 백그라운드 태스크이고, 연결이 끊기면 태스크를 취소합니다.

- 기존 원칙 "워커는 LLM을 부르지 않는다"를 유지합니다. 워커는 문서 수집만 하고, 모델 호출은 지금처럼 요청을 받은 API 프로세스가 합니다.
- 폴링 API(실행 생성 후 상태 조회)보다 단계가 생기는 즉시 화면에 보이고, 웹소켓보다 단순합니다. 화면은 인증 헤더가 필요해 `EventSource` 대신 `fetch` + `ReadableStream`으로 읽고 `AbortController`로 중지합니다.
- 진행은 DB에도 단계마다 커밋하므로, 스트림을 놓쳐도 `GET /agent/runs/{id}`로 같은 내용을 다시 볼 수 있습니다.

### 6. OpenDART 재무제표 API 추가

비율 질문은 재무상태표·손익계산서의 정확한 금액이 필요합니다. 주석 본문 검색으로 찾으면 표가 ` | `로 이은 줄이라 행·기간·단위가 섞이고, 모델이 그 줄에서 숫자를 골라야 합니다. OpenDART `fnlttSinglAcntAll.json`(단일회사 전체 재무제표)은 계정별 당기·전기 금액을 원 단위로 줍니다.

- 인자: 문서의 `corp_code`, 사업연도, 보고서 코드(사업 11011, 반기 11012, 1분기 11013, 3분기 11014), `fs_div`(기본 연결 `CFS`).
- 사업연도·분기는 저장된 `report_nm`(가져온 문서는 `사업보고서`처럼 기간이 없음) 대신 표지 청크의 "2025년 01월 01일부터 2025년 12월 31일까지"에서 읽고, 없으면 보고서명의 `(2025.12)`, 그다음 접수일(사업보고서만)로 정합니다.
- 상태 `013`(자료 없음)은 빈 목록, 그 밖의 오류는 기존 `DartError` 규칙. 응답은 `data/dart/fnltt/{corp_code}_{year}_{reprt}_{fs}.json`에 캐시합니다. Fake는 가람전자(합성)의 합성 재무제표입니다.

### 7. 로컬·Fake만 지원

`LLM_PROVIDER=real`이면 501 "에이전트는 현재 로컬 LLM에서만 지원합니다"를 돌려주고 Anthropic API를 호출하지 않습니다. 한 질문에 모델 호출이 최대 7번이고 도구 결과가 매번 쌓여 비용이 큽니다. 모델 호출마다 `llm_calls`(비용 0, `agent_run_id`)를 남깁니다.

## 대안

| 대안 | 기각 이유 |
| --- | --- |
| 모델이 계획을 먼저 세우고 실행(plan-and-execute) | 계획 단계에서 문서·계정 이름을 모르는 채로 세운 계획이 첫 결과에서 바로 어긋남. 로컬 모델은 긴 계획 JSON을 자주 깨뜨림. 계획 검증·재계획 코드가 더 필요. 단계마다 결과를 보고 고르는 지금 방식이 단순하고 기록하기 쉬움 |
| Claude tool use | 품질은 나을 수 있으나 단계마다 누적 입력 비용이 큼. 이번 목적은 "로컬 모델로 어디까지 되나"를 코드 안전장치와 함께 재는 것. 같은 도구·검증 코드에 클라이언트만 바꾸면 되므로 후속으로 남김 |
| 계산을 모델에 맡기고 결과만 검증 | 검증이 실패하면 고칠 방법이 없음(확인 필요만 늘어남). 계산 도구는 맞는 숫자를 만들 길을 줌 |
| 워커에서 에이전트 실행(작업 큐) | 워커는 LLM을 부르지 않는 원칙. 단계 실시간 표시를 위해 결국 폴링이나 별도 채널이 필요 |

## 결과와 한계

- 계산은 코드가 하므로 `K#`이 붙은 숫자는 원문 값의 정확한 계산 결과입니다. 그러나 **어떤 값을 넣을지는 모델이 고릅니다.** 부채총계 대신 유동부채를 넣으면 계산은 맞고 답은 틀립니다. 이 오류는 숫자 검증이 잡지 못하므로 화면은 `K#`의 값 출처(`F1 부채총계 당기`)를 보여 주고 판단을 담당자에게 맡깁니다.
- 숫자 검증은 "도구 결과 어딘가에 있는가"만 봅니다. 엉뚱한 근거에 있는 같은 숫자도 통과합니다.
- 숫자 없는 잘못된 서술(방향을 반대로 씀)은 잡지 못합니다.
- 별칭은 실행마다 새로 매깁니다. 같은 `D1`이 다른 실행에서는 다른 문서일 수 있어 저장된 단계는 근거 객체에 문서 정보를 함께 담습니다.
- `fnlttSinglAcntAll`은 2015년 이후 상장사 위주이고, 금융업 등 일부 회사는 계정명이 다릅니다. 일치가 없으면 계정명 목록(최대 40개)을 돌려줘 모델이 다시 고르게 합니다.
- 실측은 아직 없습니다(`evals/agent_tasks_live.jsonl`은 `_example` 행만). Fake Eval(`python -m footnote_rag.evals.agent`)은 스크립트형 모델로 루프·도구·검증이 의도대로 작동하는지만 확인합니다.
