# ADR 0012: 전기 대비 주석 변동 분석(코드가 탐지, 로컬 모델은 요청할 때만 요약)

- 상태: 채택
- 날짜: 2026-11-25
- 관련: [ADR 0008](0008-local-llm-ollama.md)(로컬 LLM), [ADR 0009](0009-prefer-consolidated-notes.md)(연결·별도 주석 키), [ADR 0010](0010-local-cascade-and-number-grounding.md)(숫자 근거 검증)

## 맥락

감사인은 매년 "전기 대비 변동 검토"를 합니다. 같은 회사의 작년 사업보고서와 올해 사업보고서에서 같은 재무제표 주석을 나란히 놓고, 새로 생긴 약정·소송, 사라진 문장, 크게 바뀐 금액, 작년 보고서와 다르게 적힌 전기 수치를 찾습니다. 주석이 30개가 넘고 표가 많아 사람이 처음부터 끝까지 대조하기 어렵습니다.

이 저장소에는 이미 필요한 재료가 있습니다. 파서(`dart/parser.py`)는 원문을 목차 경로가 붙은 섹션으로 나누고, `dart/sections.py`의 `statement_scope`·`note_key`는 연결/별도 주석을 가리고 번호·`(연결)`을 뺀 비교 키를 만듭니다. 삼성전자 2025 사업보고서를 파싱하면 연결 주석 34개가 섹션 34개이고 `note_key`도 34개입니다.

LLM에게 두 보고서를 통째로 주고 "무엇이 바뀌었나"를 물으면 길이 제한에 걸리고, 모델이 숫자를 계산·환산하다 틀리며, 같은 입력에도 결과가 달라집니다. 감사 보조 도구는 결과를 다시 만들 수 있어야 하고 숫자가 틀리면 안 됩니다.

## 결정

### 1. 역할 분담

- **코드(결정적)**: `comparison/notes.py`가 주석 짝짓기, 주석 추가·삭제, 줄 단위 비교, 표 행 숫자 비교와 증감률, 전기 수치 불일치, 관심 주석 표시, 우선순위 정렬을 모두 합니다. I/O가 없는 순수 함수라 같은 입력이면 같은 결과이고 단위 테스트로 검증합니다. 결과는 `note_comparisons.result`(JSON, 숫자는 문자열)에 저장합니다.
- **로컬 모델(요청할 때만)**: 사용자가 주석 하나에서 "요약 생성"을 누르면, 코드가 찾은 변동(바뀐 줄과 숫자 변동 표)만 모델에 보내 3~5개 항목으로 요약받습니다. 모델은 계산하지 않습니다. 요약의 숫자가 모델에게 준 자료에 없으면 `needs_review`("확인 필요")로 표시하고 `ungrounded_numbers`에 남깁니다(`answering.number_check`의 `extract_numbers`/`contains_number` 재사용, 점 천 단위 표기 `39.012` ↔ `39,012` 인정). 근거 줄 번호(`P12`/`C15`)는 자료에 실제로 넣은 줄만 남기고, 유효한 근거 줄이 없는 항목도 `needs_review`입니다. 변동의 중요성 판단은 담당자가 합니다.

### 2. 주석 짝짓기와 줄 비교

- 주석 = `statement_scope(path) == scope`(기본 연결)인 섹션을 `note_key`로 묶은 것. 같은 키의 소제목 섹션은 문서 순서대로 줄을 이어 붙입니다.
- 짝짓기: `note_key`가 같으면 짝(`key`). 남은 것끼리 `difflib.SequenceMatcher` 비율 0.85 이상을 비율이 높은 순서로 일대일 짝(`similar_title`). 그래도 남으면 당년에만 있는 주석은 `added`, 전년에만 있는 주석은 `removed`.
- 줄 비교: `SequenceMatcher`로 줄 목록을 비교합니다. 줄 번호는 주석 안에서 전년 `P{n}`, 당년 `C{n}`입니다. `replace` 블록에서 숫자를 `#`로 바꿔도 같은 줄 쌍은 `numbers_only`입니다. 매년 금액만 바뀌는 표 행이 "문장 변경"에 섞이지 않게 합니다. 주석마다 바뀐 줄은 `NOTE_DIFF_MAX_LINES`(400)개까지만 저장하고 `truncated`로 표시합니다(통계는 전체 기준).

### 3. 표 해석: 기간 블록

파서는 표를 셀을 ` | `로 이은 줄로 만듭니다. 실제 사업보고서의 주석 표는 대부분 **기간 블록**으로 나뉩니다(삼성전자 연결 주석에서 블록 표시 167곳, 한 줄에 `당기`·`전기` 열 머리글이 함께 있는 곳 10곳).

```
특수관계자거래에 대한 공시
당기 | (단위 : 백만원)
…(계층형 열 이름)…
매출 등, 특수관계자거래 | 110,512 | 67,330 | 96,962 | …
전기 | (단위 : 백만원)
…
```

- `당기 | …`, `전기`, `당기말`, `전기말`로 시작하는 줄이 블록을 엽니다. 다음 블록 표시나 숫자·`|`가 없는 설명 줄이 나오면 닫힙니다. 그 설명 줄이 다음 표의 제목입니다.
- 블록 표시처럼 시작하지만 숫자가 있는 줄(`당기 | 1,000 | 800`, 기간을 행으로 쓴 표)은 블록 표시가 아니라 그 기간의 데이터 행입니다.
- 한 줄에 `당기`·`전기` 셀이 함께 있는 머리글이면 열 형태로 보고, 아래 행의 첫 값을 당기, 둘째 값을 전기로 씁니다. 머리글에서 `당기`가 먼저일 때만 그렇게 하고, 아니면 그 표는 숫자 비교에서 뺍니다.
- 행 이름 = 첫 숫자 앞의 비숫자 셀들, 값 = 숫자 셀들(`1,234`, `(1,234)`·`△1,234` 음수, `-` = 0, `%`). 날짜와 4자리 연도 단독 셀은 숫자가 아닙니다.
- 행 식별자 = (표 제목, 행 이름, 같은 기간·제목·이름 안에서의 순번).

**한계**

- 계층형 열 이름(여러 줄에 걸친 머리글)은 복원하지 않습니다. 값은 **위치로만** 비교합니다(`(2열)`). 두 해의 열 구성이 바뀌면 값 개수가 달라져 증감 없이 값 목록만 나란히 둡니다.
- 같은 (제목, 행 이름)이 여러 번 나오는데 두 보고서의 개수가 다르면 순번으로 짝지을 수 없습니다. 이 행들은 비교하지 않고 `ambiguous_rows`로 셉니다(화면 "비교 보류 행"). 개수가 같으면 순번으로 비교합니다.
- 단위(백만원/천원) 환산은 하지 않습니다. 한 해만 단위가 바뀌면 큰 변동으로 보일 수 있습니다.
- `large_change`는 |증감|/|전년| ≥ `NOTE_DIFF_CHANGE_THRESHOLD`(0.3), 부호 반전, 0 → 0 아님입니다. `%` 셀이 있거나 값이 모두 1 미만인 비율 행은 표시하지 않습니다.

### 4. 전기 수치 불일치

당년 보고서의 전기 행(같은 식별자)이 전년 보고서의 당기 행과 다르면 `prior_mismatch`입니다. 회계정책 변경에 따른 재작성, 재분류, 표 구성 변경, 또는 단순한 행 이름 중복일 수 있습니다. **후보일 뿐 판단이 아닙니다.** 화면은 "당년 보고서의 전기 값 vs 전년 보고서의 당기 값"으로 따로 보여 주고 판단은 담당자에게 맡깁니다. 큰 변동 표시는 전년 대비(`yoy`)에만 붙입니다.

### 5. 관심 주석과 우선순위

`NOTE_DIFF_WATCHLIST`(우발부채, 약정, 소송, 특수관계자, 담보, 지급보증, 보고기간후사건, 계속기업, 회계정책의변경)의 단어가 `note_key`에 있으면 관심 주석입니다. 점수 = 관심 주석 1000 + 주석 추가·삭제 40 + 전기 불일치 15/건 + 큰 변동 5/건 + 문장 변경 줄 1/줄(최대 50). 변동 없는 주석은 0입니다. 관심 주석 가중치를 다른 항목의 합보다 크게 잡아, 바뀐 관심 주석이 항상 먼저 옵니다.

### 6. Claude 미지원

요약은 `LLM_PROVIDER=local`(Ollama)과 `fake`만 지원합니다. `real`이면 501 "변동 요약은 현재 로컬 LLM에서만 지원합니다"를 돌려주고 Anthropic API를 호출하지 않습니다. 주석 하나의 변동 자료는 수천 자이고 사용자가 여러 주석을 반복해 요약할 수 있어 호출 비용이 쌓입니다. 요약은 계산이 없는 보조 기능이라 로컬 모델로 충분하다고 봤습니다. 상향(cascade)도 쓰지 않고 `LOCAL_LLM_MODEL` 하나로 돌립니다. 이를 위해 `OllamaClient`에 범용 `chat_json`(JSON 스키마 강제 출력, 기존 오류 매핑·재시도 1회 재사용)을 추가했고 `answer` 동작은 바꾸지 않았습니다.

## 대안

| 대안 | 기각 이유 |
| --- | --- |
| XBRL 재무제표 API(`fnlttSinglAcntAll`)로 정형 숫자 비교 | 재무제표 본문 계정만 있고 주석 문장·주석 표 대부분이 없음. 주석 변동 검토의 핵심(약정·소송 문장, 특수관계자 표)을 못 봄. 숫자 정확도를 높이는 보완책으로는 후속 검토 가치가 있음 |
| 모델이 두 주석을 직접 비교 | 긴 주석은 `num_ctx`를 넘고, 모델이 숫자를 계산·환산하다 틀리며, 결과가 재현되지 않음. 무엇을 놓쳤는지 알 수 없음 |
| 질문 답변(RAG) 흐름으로 "작년과 달라진 점" 질문 | 검색 상위 k개만 보므로 변동 전체를 덮지 못함 |
| 표를 HTML 그대로 보관해 셀 좌표로 비교 | 파서·청크·임베딩 전체를 바꾸는 일. 이번 범위 밖 |

## 결과와 한계

- 비교는 모델 호출 없이 끝나고 같은 입력이면 같은 결과입니다. 원문 ZIP은 `data/dart` 캐시를 다시 씁니다.
- 숫자 비교 품질은 표 구조에 달려 있습니다. 계층형 열과 중복 행은 위치 비교·비교 보류로 처리하므로, 놓친 변동은 줄 비교(숫자만 바뀐 줄)에서 확인해야 합니다.
- 요약 검증은 숫자와 근거 줄 번호만 봅니다. 숫자 없는 잘못된 서술(예: 방향을 반대로 씀)은 잡지 못합니다. 그래서 화면에 항상 "모델 요약 — 변동 판단은 담당자가 확정"을 표시합니다.
- 정답 데이터(`evals/note_changes.jsonl`)는 실제 3쌍에서 사람이 확인한 변동만 넣습니다. 구현 환경에 원문·키가 없어 아직 예시 행만 있고 실측은 미측정입니다. 확인한 항목은 `python -m footnote_rag.evals.validate_note_changes`로 인용문이 파싱된 주석에 실제로 있는지 검사합니다.
