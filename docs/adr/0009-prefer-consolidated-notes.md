# ADR 0009: 연결재무제표 주석 우선 정책

- 상태: 채택
- 날짜: 2026-11-25
- 관련: [ADR 0002](0002-claude-citations-search-result.md)(Claude Citations), [ADR 0006](0006-annual-report-a001.md)(사업보고서 A001), [ADR 0008](0008-local-llm-ollama.md)(로컬 LLM)

## 맥락

사업보고서(A001)에는 같은 주석이 두 번 나옵니다. `III. 재무에 관한 사항 > 3. 연결재무제표 주석` 아래에 한 번, `5. 재무제표 주석`(별도) 아래에 또 한 번입니다. 두 주석은 제목과 문장이 거의 같아서 임베딩 유사도도 비슷하고, 별도 주석이 더 높게 나올 때가 많습니다.

2026-11-25 로컬 모델(`ollama:qwen3:14b`) 실측([리포트](../../evals/reports/20261125T020155Z-live-local-qwen3-14b.md))의 결과는 다음과 같습니다.

- recall@8 95.2%. 인용 정확도 61.3%(19/31), 검색 성공 문항만 보면 63.3%.
- 틀린 각주 12개 중 **9개**가 기대 섹션(연결 주석)과 같은 주석을 **별도 주석**에서 인용한 경우였습니다(samsung-01, samsung-02, samsung-04, naver-01, hyundai-04, compare-03의 4개).
  - 예: 기대 `3. 연결재무제표 주석 > 12. 차입금 (연결)` / 인용 `5. 재무제표 주석 > 12. 차입금`.
  - 이 문항들에서는 기대 섹션이 대부분 검색 1~4위 안에 있었습니다. 다만 별도 주석 청크가 더 높은 순위인 경우가 많았습니다.
- 나머지 3개는 실제 오류였습니다. naver-02는 검색 실패, naver-04는 다른 연결 주석 인용, hyundai-03은 회계정책 인용입니다.

한국 공시에서 주된 재무제표는 연결재무제표입니다. K-IFRS 1110은 지배기업에 연결재무제표 작성을 요구하고, 별도재무제표(K-IFRS 1027)는 그와 함께 내는 지배기업 단독의 재무제표입니다. 사업보고서도 연결재무제표와 그 주석을 먼저 싣습니다. 질문이 "별도"를 지정하지 않으면 연결 주석이 맞는 근거입니다.

같은 주석이라도 번호와 제목이 다를 수 있습니다.

- 현대차: 연결 `35. 특수관계자 등과의 거래 (연결)`, 별도 `33. 특수관계자 등과의 거래`.
- 현대차: 연결 `2. 연결재무제표 작성기준 및 중요한 회계정책 (연결)`, 별도 `2. 재무제표 작성기준 및 중요한 회계정책`.

## 결정

1. **주석 종류 판별**(`src/footnote_rag/dart/sections.py`)
   - `statement_scope(section_path)`는 상위 경로의 `…재무제표 주석`(또는 `…재무제표 > 주석`)을 보고 판별합니다. `연결`이 있으면 `consolidated`, 없으면 `separate`, 주석이 아니면 `None`입니다.
   - `note_key(section_path)`는 주석 소제목에서 앞 번호, `(연결)` 접미사, 공백, "연결"을 지운 비교 키입니다(`12. 차입금 (연결)` → `차입금`). 그래서 번호가 다르거나 "연결재무제표"/"재무제표"로 문구가 달라도 같은 키가 나옵니다.
   - `is_counterpart(a, b)`는 한쪽이 연결이고 다른 쪽이 별도이며 키가 같으면 참입니다.
2. **검색 재정렬**(`retrieval.search.prefer_statement_scope`, `PREFER_CONSOLIDATED` 기본 `true`)
   - 벡터 검색은 후보를 `max(TOP_K, RETRIEVAL_CANDIDATES)`개(기본 16) 가져옵니다.
   - 같은 문서 안에 연결 주석과 그 대응 별도 주석이 둘 다 후보에 있으면, 별도 청크를 모든 후보 뒤로 보냅니다. 나머지는 유사도 순서를 지킵니다. 그다음 앞에서부터 `TOP_K`개를 고릅니다. 별도 청크는 없애지 않으므로 자리가 남으면 들어갑니다.
   - 질문에 "별도" 또는 "개별"이 있으면 반대로 연결 청크를 뒤로 보냅니다.
   - `PREFER_CONSOLIDATED=false`이면 지금까지와 같이 `TOP_K`개를 유사도 순으로 가져옵니다.
   - `POST /search`, 답변, Eval 진단은 모두 재정렬된 최종 순서를 씁니다(`answering.service.retrieve`).
3. **신뢰도 규칙 유지**: `MIN_RETRIEVAL_SCORE`는 **재정렬 전 후보의 최고 유사도**와 비교합니다. 재정렬은 어느 근거를 먼저 보여 줄지만 정할 뿐, 검색이 질문과 얼마나 가까웠는지는 바꾸지 않기 때문입니다. 1위 별도 청크가 뒤로 밀려 최종 목록에서 빠져도, 같은 내용의 연결 청크가 남으므로 신뢰도 판단을 낮출 이유가 없습니다. 감사 로그의 `top_score`도 같은 값입니다.
4. **프롬프트 규칙**(`answering/prompt.py`)
   - Claude와 로컬 시스템 프롬프트 모두에 규칙을 넣었습니다. "같은 내용이 연결재무제표 주석과 (별도)재무제표 주석에 모두 있으면, 질문이 별도재무제표를 지정하지 않는 한 연결재무제표 주석을 근거로 인용한다."
   - 근거 제목에 `[연결]`/`[별도]` 표시를 붙입니다. 예: `삼성전자 사업보고서 · [연결] III. … > 12. 차입금 (연결)`. Claude의 `search_result` `title`과 로컬 프롬프트의 근거 머리줄이 같은 제목을 씁니다.
   - 시스템 프롬프트는 고정 문자열로 둡니다. 요청마다 바뀌는 값을 넣지 않으므로 프롬프트 캐시가 깨지지 않습니다.
5. **Eval 보조 지표**(`evals/run.py`)
   - 기존 인용 정확도(기대 접두어 일치)는 이름과 값을 그대로 둡니다.
   - 새 지표 **citation accuracy (consolidated/separate counterpart accepted)**를 추가합니다. 기대 섹션의 대응 주석을 인용한 각주도 맞음으로 셉니다. 전체, 검색 성공 문항, 유형별 표에 모두 냅니다.
   - Citation diagnostics의 각주 표에 `counterpart` 열을 추가했습니다. 진단 문구는 "separate-statement counterpart cited"와 "the model cited other evidence"를 구분합니다.
   - 답할 수 있는데 거절한 문항마다 `review_reason`과 검색 상위 k 표를 냅니다.
   - 리포트 머리말에 `prefer_consolidated`와 `retrieval_candidates`를 적습니다.

## 역할 분담: 재정렬과 프롬프트

| 수단 | 맡는 일 | 혼자로는 부족한 이유 |
| --- | --- | --- |
| 재정렬 | 연결 주석이 근거 목록 앞쪽에 오게 하고, 후보를 넓혀 9위 이하의 연결 주석도 들어오게 함 | 별도 청크가 자리가 남아 목록에 남으면, 모델이 여전히 그것을 고를 수 있음 |
| 프롬프트 규칙 + `[연결]`/`[별도]` 표시 | 둘 다 보일 때 어느 쪽을 인용할지 모델에게 알려 줌 | 경로 문자열만으로는 작은 모델이 연결/별도를 잘 가리지 못함. 또 근거 목록에 연결 주석이 없으면 규칙을 지킬 수 없음 |

재정렬은 서버가 결정적으로 보장하는 부분이고, 프롬프트는 모델의 선택을 돕는 부분입니다. 그래서 두 가지를 함께 씁니다.

## 엄격 지표를 유지하고 대응 인정 지표를 따로 둔 이유

- 데이터셋의 기대 섹션은 연결 주석이고, 정책도 연결 주석 인용이 맞다는 것입니다. 엄격 지표는 정책을 지켰는지 재는 지표이므로 바꾸지 않습니다. 대응 주석을 맞음으로 바꾸면 이번 변경의 효과가 지표에서 보이지 않습니다.
- 별도 주석을 인용한 답이 사실관계까지 틀린 것은 아닙니다. 대응 인정 지표는 "엉뚱한 근거"와 "같은 주석의 다른 재무제표 판"을 나누어 실제 오류 크기를 보여 줍니다. 이번 실측에 적용하면 19/31에서 28/31이 됩니다.
- 두 지표의 차이가 남아 있는 연결↔별도 혼동의 크기입니다. 재정렬과 프롬프트가 잘 작동하면 이 차이가 줄어야 합니다.
- 데이터셋 문항이나 기대 섹션은 바꾸지 않았습니다. 기대 섹션을 별도 주석까지 넓히면 과거 리포트와 비교할 수 없게 됩니다.

## 대안

| 대안 | 기각 이유 |
| --- | --- |
| 별도 주석 청크를 검색에서 아예 제외 | 별도 기준 질문("별도재무제표상 종속기업 투자")에 답할 수 없음. 별도에만 있는 주석도 있음 |
| 연결 청크 점수에 고정 가산점 | 가산점 크기를 데이터마다 조정해야 하고, 대응 주석이 없는 연결 청크까지 올라감 |
| 외부 재정렬 모델(Voyage rerank 등) | 비용과 의존성이 늘고, 연결/별도 구분이라는 도메인 규칙을 보장하지 못함. 이번 범위 밖 |
| 청킹 때 연결/별도 주석을 하나로 병합 | 재처리가 필요하고, 두 판의 숫자가 다른 경우 근거 위치가 흐려짐 |
| 데이터셋 기대 섹션에 별도 주석 추가 | 정책상 정답이 아님. 과거 리포트와 비교가 끊김 |

## 결과와 한계

- 질문에 "별도"·"개별"이라는 단어가 다른 뜻으로 들어가도 별도 우선이 됩니다(예: "별도로 공시된…"). 이 경우에도 연결 청크는 없어지지 않고 뒤로만 갑니다.
- `note_key`는 제목 문자열로 비교합니다. 두 판의 제목이 크게 다르면(예: 한쪽만 "및 사채"가 붙음) 대응으로 보지 않고 재정렬도 하지 않습니다. 이 경우 동작은 기존과 같습니다.
- 검색 후보를 16개로 늘려 pgvector 조회량이 조금 늘었습니다. HNSW iterative scan이므로 영향은 작습니다.
- 효과는 머지 후 같은 데이터셋으로 `--live`를 다시 돌려 확인합니다. 리포트 머리말의 `prefer_consolidated`로 설정별 결과를 비교할 수 있습니다.
