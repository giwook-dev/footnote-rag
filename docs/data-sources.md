### 왜 감사보고서(F001/F002)가 아니라 사업보고서(A001)인가

- 같은 날 같은 기간으로 F001(감사보고서)·F002(연결감사보고서)를 조회하면 세 회사 모두 **0건**이었습니다.
- 상장사는 외부감사인의 감사보고서를 별도 공시(`pblntf_ty=F`)로 내지 않습니다. 감사받은 (연결)재무제표와 주석, 감사의견은 정기공시인 **사업보고서**(`pblntf_ty=A`, `pblntf_detail_ty=A001`) 안에 들어 있습니다. F001/F002로 별도 공시되는 것은 주로 비상장 외부감사 대상 회사의 감사보고서입니다.
- 그래서 검색·가져오기의 기본 종류를 A001로 바꿨습니다(→ [ADR 0006](adr/0006-annual-report-a001.md)). F001/F002 검색은 비상장사용으로 남겨 두었습니다. 웹 화면은 F001/F002 검색 결과가 0건이면 "상장사는 감사보고서를 사업보고서(A001)에 포함해 공시합니다."라고 안내합니다.

재현 명령(키를 `.env`에 넣은 뒤):

```bash
python -m footnote_rag.cli dart-find   --stock-codes 005930,035420,005380 --from 20260101 --to 20260531   # --detail A001이 기본값
python -m footnote_rag.cli dart-fetch --rcept-no 20260310002820   # 원문 ZIP 캐시 + 목차 확인
```

PowerShell에서는 쉼표로 구분한 종목코드를 따옴표로 감싸야 합니다(`--stock-codes "005930,035420,005380"`). 따옴표가 없으면 PowerShell이 배열로 해석하면서 앞자리 0이 사라집니다.

## 수집 방법

1. `corpCode.xml`(ZIP)을 받아 종목코드 → 고유번호(corp_code)를 찾습니다. `data/dart/corp_codes.json`에 7일 캐시합니다(상장사만 저장).
2. `list.json`에 `corp_code`, 기간, `pblntf_ty`(종류 코드의 첫 글자: A001 → `A`, F001/F002 → `F`), `pblntf_detail_ty`(기본 `A001`), `last_reprt_at=Y`(최종 보고서만)를 넣어 접수번호를 찾습니다. 여러 페이지면 모두 읽습니다. `013`(데이터 없음)은 빈 목록으로 처리합니다.
3. `document.xml?rcept_no=`로 원문 ZIP을 받아 `data/dart/{rcept_no}.zip`에 저장하고, 있으면 재사용합니다. ZIP 대신 JSON/XML 오류 본문이 오면 `status` 코드로 분류합니다.
4. 원문 XML을 목차 경로별 섹션으로 파싱하고(→ [ADR 0004](adr/0004-opendart-xml-over-pdf.md)), 청킹·임베딩 후 pgvector에 저장합니다.
5. (에이전트의 `get_financials` 도구만) `fnlttSinglAcntAll.json`(단일회사 전체 재무제표)에 `corp_code`, `bsns_year`, `reprt_code`(사업 11011, 반기 11012, 1분기 11013, 3분기 11014), `fs_div`(연결 `CFS`/별도 `OFS`)를 넣어 계정별 당기·전기 금액(원)을 받습니다. 사업연도·분기는 표지의 보고 기간에서 읽습니다. 정상 응답은 `data/dart/fnltt/{corp_code}_{year}_{reprt}_{fs}.json`에 캐시하고, `013`(자료 없음)은 빈 목록입니다(→ [ADR 0013](adr/0013-tool-using-agent.md)). 문서 수집 워커는 이 API를 부르지 않습니다.

요청 URL은 로그에 남기되 `crtfc_key`는 `***`로 마스킹합니다. httpx 자체 요청 로그는 꺼 두었습니다.

### 원문 XML 오류 문자와 정리 규칙

DART 원문 XML은 올바른 XML이 아닙니다. 파서는 lxml 복구 모드(`recover=True`)로 읽습니다. 아래 오류를 만나면 그 뒤의 `SECTION`/`TITLE` 구조를 잃어 여러 장이 한 섹션으로 뭉치거나, 루트 요소가 일찍 닫혀 뒤쪽 장을 통째로 버립니다. 2026-11-25에 세 회사 2025 사업보고서로 확인했습니다.

| 오류 | 원문 예 | 개수 (삼성 / NAVER / 현대차) |
| --- | --- | --- |
| 텍스트 안의 이스케이프되지 않은 `&` | `Place&JAPAN Co., Ltd`, `S&P(미국)` | 972 / 137 / 1,044 |
| 텍스트 안의 글자 그대로의 `<` | `<개정 2015.03.20>`, `<신  설>`, `< TV 시장점유율 추이 >` | 8 / 50 / 20 |
| 큰따옴표가 겹친 속성값 | `<TE ENG=""Snow Corporation" …>` | 0 / 2 / 4 |
| 영문 시작 태그처럼 보이는 본문 | `<P USERMARK="B"><Manufacturing Excellence></P>`, `<Advanced Tech &amp; SDV>` | 0 / 0 / 4 |

- 한글은 XML 이름에 쓸 수 있는 글자입니다. 그래서 `<신  설>`은 닫히지 않은 시작 태그로 읽히고, 뒤의 섹션이 모두 그 안으로 들어갑니다. 정리 단계가 없던 파서로는 NAVER가 11개 섹션(`II. 사업의 내용 > 5. 위험관리 및 파생거래` 한 섹션에 약 869,000자), 현대차가 6개 섹션(`I. 회사의 개요 > 5. 정관에 관한 사항` 한 섹션에 약 755,000자)으로 나왔습니다.
- 속성 따옴표 오류와 영문 가짜 태그는 태그 짝을 어긋나게 만듭니다. `&`·`<`만 정리하면 libxml2가 루트 요소를 일찍 닫습니다(`ERR_DOCUMENT_END`, "Extra content at the end of the document"). 그러면 복구 모드가 그 뒤 내용을 버립니다. 실제로 그렇게만 정리했을 때 NAVER·현대차는 `IV. 이사의 경영진단 및 분석의견` 이후 장(감사의견·임원·주주 등)이 출력에서 사라졌습니다. 현대차는 `III. 재무에 관한 사항`이 `II. 사업의 내용` 아래로 중첩되기도 했습니다.

정리 규칙(`src/footnote_rag/dart/parser.py`의 `sanitize_dart_xml`): `parse_document_xml`이 파싱 직전에 **바이트 단위로** 아래 네 가지를 차례로 치환합니다. ZIP 가져오기, `cli dart-fetch`, `evals.validate`가 모두 이 함수를 거치므로 정리는 한 곳에서만 일어납니다.

1. `&(?!(?:[A-Za-z][A-Za-z0-9]*|#[0-9]+|#x[0-9A-Fa-f]+);)` → `&amp;`: 엔티티 참조(`&amp;`, `&lt;`, `&#39;`, `&#x27;`)가 아닌 `&`만 바꿉니다. 정상 엔티티는 이중 이스케이프되지 않습니다.
2. `<(?!/?[A-Za-z][A-Za-z0-9_.:-]*(?:[\s/>])|!|\?)` → `&lt;`: 영문 태그·닫는 태그·`<!-- -->`·`<![CDATA[`·`<?xml`이 아닌 `<`만 바꿉니다.
3. `=""(?=[^"\s>])` → `="&quot;`: 큰따옴표가 겹쳐 열린 속성값(`ENG=""Snow Corporation"` → `ENG="&quot;Snow Corporation"`)만 바꿉니다. 빈 값(`ALIGN=""`)은 그대로 둡니다.
4. `<(?=[A-Za-z][A-Za-z0-9_.:-]*\s+[^\s=/>]+(?:\s+[^\s=/>]+)*\s*>)` → `&lt;`: 태그 이름 뒤의 낱말에 `=`이 하나도 없는 "시작 태그"(`<Manufacturing Excellence>`)만 바꿉니다. 값 없는 속성은 XML에서 항상 오류라서 이런 문자열은 본문 글자입니다. 개별 문서용 교정이 아니라 일반 규칙입니다. `<P USERMARK="B">`, `<IMG SRC="x"/>`, `<P >`처럼 올바른 태그는 바뀌지 않습니다.

- 패턴은 ASCII `&`(0x26)·`<`(0x3C)·`"`·`=`만 봅니다. 이 바이트는 UTF-8과 EUC-KR/CP949의 다바이트 문자 안에 나오지 않으므로 디코딩 전에 적용해도 안전합니다.
- 파싱 후 텍스트에는 원래 문자(`Place&JAPAN`, `<개정 2015.03.20>`, `<Manufacturing Excellence>`)가 그대로 남습니다.
- 그 밖의 오류는 복구 모드에 맡깁니다.
- 치환 개수는 `ParsedDocument.sanitized`(`bare_amp`, `bare_lt`, `bad_attr_quote`, `pseudo_tag`)와 로그 `dart.sanitized`에 남습니다. `dart-fetch` 출력 첫 줄에도 표시됩니다. 예: `== 20260318001394: 현대자동차(주) 사업보고서 (125 sections) (sanitized &:1044 <:20 attr:4 tag:4)`.
- **분해 품질 경고**: 가장 큰 섹션이 전체 텍스트의 50%를 넘고 섹션이 20개 미만이면 경고 로그 `dart.parse_suspicious`를 남깁니다. 실패로 처리하지는 않습니다.
- **잘림 경고**: 정리 후에도 libxml2가 `ERR_DOCUMENT_END`를 내면(루트 뒤 내용 폐기) 경고 로그 `dart.parse_truncated`(줄 번호 포함)를 남기고 `ParsedDocument.truncated=True`로 둡니다. 이때 `dart-fetch` 첫 줄 끝에 `TRUNCATED`가 붙습니다. 이것도 실패로 처리하지는 않습니다.

Eval 데이터셋의 `expected_section_prefixes`는 현재 파서가 만든 경로를 그대로 씁니다. 따라서 파서 규칙이 바뀌어 경로가 달라지면 `evals.validate`가 오류를 내고, 그때 데이터셋도 함께 고쳐야 합니다.

파서 규칙:

| 요소 | 처리 |
| --- | --- |
| (파싱 전) 맨 `&`, 태그가 아닌 `<`, 겹친 속성 따옴표, 영문 가짜 태그 | `&amp;`, `&lt;`, `&quot;`로 이스케이프(위 정리 규칙) |
| `DOCUMENT-NAME` | 보고서명(문서 제목 일부) |
| `COMPANY-NAME`(`AREGCIK` 속성) | 회사명, corp_code |
| `BODY` | 본문 시작점 |
| `COVER` / `COVER-TITLE` | 표지 섹션(`사업보고서`) |
| `SECTION-1/2/3…` + 첫 `TITLE` | 목차 경로. 자간이 벌어진 제목(`재 무 상 태 표`)은 붙여 씀 |
| `LIBRARY` 등 제목 없는 컨테이너 | 투명하게 통과 |
| `P`, `SPAN` 등 | 본문 텍스트 |
| `TABLE` > `TR` > `TH/TD/TE/TU` | 행 단위 `셀 | 셀` |
| 주석 섹션(제목에 "주석") 안의 추가 `TITLE` | 주석 소제목. 새 하위 목차(`… 주석 > 1. 일반적 사항 (연결)`)를 시작하고, 소제목 텍스트는 본문에 넣지 않음. 첫 소제목 앞 본문은 주석 섹션 경로에 남음 |
| 주석 섹션 안의 `TITLE`을 가진 컨테이너(`TABLE-GROUP`) | 펼쳐서 위 규칙을 그대로 적용 |
| 주석 섹션의 `12. 리스` 같은 짧은 번호 문단 | 그 주석 섹션에 `TITLE` 소제목이 하나도 없을 때만 하위 목차로 승격(이중 승격 방지) |
| `가.`, `나.` 수준 제목 | 나누지 않음 |

파서를 바꾼 뒤 이미 가져온 문서는 웹 화면의 **다시 처리** 버튼(admin), `POST /documents/{document_id}/reprocess`, 또는 `python -m footnote_rag.cli dart-reprocess`로 다시 파싱합니다. 원문 ZIP 캐시를 재사용하므로 다시 내려받지 않습니다.

## 원문을 커밋하지 않는 이유

- 공시 원문은 회사와 금융감독원 DART의 자료이고, 이 저장소의 목적은 수집·검색·인용 **파이프라인**을 보여 주는 것입니다. 원문 재배포는 필요하지 않습니다.
- 원문 ZIP은 수 MB이고 언제든 접수번호로 다시 받을 수 있어 저장소에 둘 이유가 없습니다.
- 그래서 `data/`(ZIP, corpCode 캐시, 업로드 파일)는 `.gitignore`와 `.dockerignore`에 들어 있고, 테스트는 테스트 코드가 직접 만든 소형 **합성** XML/ZIP만 씁니다.
- Fake 모드에서 받은 합성 데이터는 `data/dart/fake/`에 따로 캐시되어 실제 다운로드와 섞이지 않습니다.

## Eval 데이터셋 상태

`evals/dataset.jsonl`에는 세 회사 2025 사업보고서(위 표의 `rcept_no`)로 작성한 질문이 **25개** 있습니다(2026-11-25). 형식 예시 행(`_example`)은 없습니다. 질문과 근거는 정리 규칙이 반영된 파서의 출력(section_path와 섹션 텍스트)을 읽고 작성했습니다.

| 구분 | id | 개수 | 다루는 섹션 |
| --- | --- | --- | --- |
| 삼성전자 | `samsung-01`~`06` | 6 | 주석: 회계처리방침(리스), 차입금, 우발부채와 약정사항(2), 계약부채. 감사: `V. 회계감사인의 감사의견 등 > 1. 외부감사에 관한 사항` |
| NAVER | `naver-01`~`06` | 6 | 주석: 회계정책(리스 할인율, 수익인식), 차입금 및 사채, 우발채무 및 약정사항(2). 감사: 회계감사인 변경 |
| 현대자동차 | `hyundai-01`~`05` | 5 | 주석: 리스 및 운용리스자산, 충당부채, 특수관계자 등과의 거래, 회계정책(수익인식). 감사: 감사보수·감사시간 |
| 비교 | `compare-01`~`04` | 4 | 리스부채 할인율(세 회사), 공정거래법상 기업집단 소속회사의 특수관계자 설명(삼성·NAVER), 수익인식 기준(삼성·현대차), 외부감사인(세 회사) |
| 답할 수 없음 | `unans-01`~`04` | 4 | 2027년 매출 전망, 대표이사 개인 주소, 다른 회사(테슬라)의 수치, 보고기간 뒤 분기 실적 |

- 행 형식은 `src/footnote_rag/evals/dataset.py`를 따릅니다. 비교 질문은 `rcept_no`·`corp_name`·`evidence_quote`를 회사 순서대로 목록으로 적고, `expected_section_prefixes`에 회사별 접두어를 모두 넣습니다. 답할 수 없는 질문은 `"answerable": false`, `"expected_section_prefixes": []`, `"evidence_quote": null`입니다.
- `evidence_quote`는 파서가 뽑은 텍스트에서 그대로 복사한 20~150자 문장입니다. 감사인 이름·보수처럼 표에만 있는 값(`hyundai-05`, `compare-04`의 현대차 인용)은 파서가 만든 표 행(`셀 | 셀`)을 그대로 옮겼습니다.
- `expected_section_prefixes`는 실제 section_path의 접두어이고, 주석이면 주석 번호 소제목까지 적었습니다.

검증 방법:

```bash
# 원문 ZIP을 data/dart/{rcept_no}.zip에 둔 뒤(dart-fetch가 이 경로에 캐시합니다)
python -m footnote_rag.evals.validate                         # 기본: --dataset evals/dataset.jsonl --zip-dir data/dart
python -m footnote_rag.evals.validate --zip-dir /다른/경로/dart   # DATA_DIR를 바꿨다면 그 아래 dart 폴더를 지정
```

- validate는 `--zip-dir`(기본 `data/dart`, 현재 작업 폴더 기준)에서 `{rcept_no}.zip`을 직접 읽습니다. `DATA_DIR` 설정은 읽지 않습니다.
- 답할 수 있는 행마다 인용문이 파서 텍스트에 있는지, 기대 접두어 아래 섹션에 있는지 검사합니다. 개수 규칙(15행 이상, 회사별 4행 이상, 답할 수 없는 질문 3개 이상, 비교 2개 이상)도 검사합니다. 성공하면 `checked rows: 25 … OK`가 출력됩니다.
- 원문이 없으면 행마다 `… missing - download it first` 오류를 내고 종료 코드 1로 끝납니다. CI에는 원문이 없으므로 CI는 validate CLI를 실행하지 않습니다. 대신 pytest의 `tests/test_evals_cli_mcp.py`가 두 가지를 검사합니다. (1) 원문이 없을 때 오류가 `missing`뿐이고 개수 규칙은 통과하는지. (2) 데이터셋 구성(id 형식, 회사별 단일 질문 4개 이상, 비교·답할 수 없는 질문 개수, 인용문 길이)이 맞는지. 원문이 `data/dart/`에 있는 개발 환경에서는 같은 테스트가 인용문까지 검증합니다.
- 키가 있으면 `python -m footnote_rag.evals.run --live`로 리포트를 만들고 비용을 리포트에 남깁니다(머지 후 별도 작업).
